1 背景与问题定义 Motivation & Problem

核心问题：如何让一个 AI 修 Bug 系统根据执行反馈持续改进自己，同时严格保证它不会越改越坏？

AI 修 Bug（automated bug fixing / SWE agent）系统的能力很大程度取决于其执行 harness——角色技能、验证策略、循环策略等"系统提示与流程代码"。我们观察到一个普遍矛盾：

  • 改进机会局部存在：对失败案例做归因后，往往能找到"应该补的指引"（例如"先枚举需求再动手"）；
  • 但改动会全局扩散：同一份 Writer 技能文件服务所有案例，为一个失败案例加的指引可能扰动其他原本通过的案例。

这就形成了本实验的核心方法论主张：系统的自我修改必须被当作"受控实验"对待——每次修改是一个候选（candidate），必须在全量回归集上重测，任何回归立即回滚；只有在演化集有增益且回归集全绿的候选才能保留为新基线。

1.1 三个子问题

  1. 演化：如何从执行结果中形成可检验的修改假设，并通过受治理的通道落地？
  2. 不退化：如何用机器可执行的硬门（而非人工目测）保证每个保留的候选不弄坏任何已通过的案例？
  3. 可信评测：如何保证评测本身不被污染（受测系统看不到答案、记忆不可漂移、报告不可篡改、断点可续跑）？

1.2 与既有工作的差异

常见做法是"跑一遍 benchmark → 人工改 prompt → 再跑一遍"，既无逐案例配对控制，也无回归保障，更无修改过程的审计链。本实验把这一过程工程化为一个可复现、可审计、可断点续跑的闭环协议（详见 §3、§6），相当于给"prompt/技能演化"建立了类似 CI 的守门机制。

2.1 关键设计原则

  • 路径不是身份，内容才是：所有绑定（协议、装置、manifest、基线、回执）一律用 SHA-256 摘要；复制路径不等于复制权威。
  • 最小信息释放：Operator（提出修改的一方）只能看到演化失败集的"投影包"（source-projection-bundle）——不含 gold 补丁、隐藏测试、通过案例的身份。这防止"照着答案改系统"。
  • 单一开放意图：每个案例/阶段同时最多一个 open intent，崩溃后按 §2.5 规则和解，不重复执行已完成的 Writer 调用。
  • 非对称信任：候选代码不能自证清白——guard 身份检查只信任"受保护检出 + 干净树 + HEAD==trusted_ref"的调用环境。

2.2 Eval 平面核心组件的实现细节

(a) Qualification 资格机制——先证明"考题本身有效"

每个案例在进入实验前必须通过资格校验（schema autobugfix-swe-qualification-v5）：

  • gold ×2：官方 gold 补丁贴入官方镜像跑两遍官方测试，必须两次全绿（证明测试与镜像可复现）；
  • null ×1：不贴补丁跑一遍，必须不绿（证明测试确实区分了修复与否，防"假阳性考题"）；
  • 镜像钉死：记录镜像 source_ref / manifest digest / receipt digest，运行时逐一比对，不接受漂移；
  • 资格记录绑定 evaluator_runtime_id（对 scorer 相关源码文件 + harness 锁文件的摘要）——评测器代码一变，全部资格自动失效，必须重盖，防止"换尺子量旧数据"。

(b) Protocol / Apparatus / Manifest 三层冻结

层内容作用
Protocol模型、档位、尝试数、超时、数据集钉死、Memory fixture、执行白名单、可见性调度实验的"物理常数"
Apparatus5 项源检查（compileall / 角色技能校验 / git diff --check / benchmark doctor / 全量 pytest）+ 协议 + SWE 协议的联合回执证明"装置此刻是绿的"
Manifest精确有序案例列表、仓库/难度/切片、H0 subject SHA/tree、OCI 镜像摘要、各平面根路径实验的物料清单

三者互相摘要绑定；study 初始化时再校验 HEAD == apparatus_sha 且工作树干净——实验运行期间代码动一行都会被拒。

(c) Subject Broker——受测主体的沙箱执行

受测系统（= 本仓库的某个冻结提交）不直接在本机跑，而是：

  1. 物化到 benchmark-cache/subjects/<sha>（PYTHONPATH 指向该快照）；
  2. 在 bwrap 气泡沙箱内运行 subject 进程：只读绑定主体代码与 Python 运行时、只写绑定任务工作树、--unshare-pid/net、凭据路径不可见、隐藏路径清单生效；
  3. 外层沙箱内若再派生 codex 会话则内层降级 full-access（修复 #1，见 §11）——因为内核禁用了非特权嵌套 user namespace；
  4. 执行全程写执行账本：每次 codex 调用前后计算补丁 SHA-256，验证器开始前再次比对（"补丁未在传输中被调包"）。

(d) 双层验证——可见验证器 vs 官方隐藏测试

可见验证器（visible verifier）：任务工作树自带的公开测试，Writer 可见、可在本地跑——它是循环的停机信号（通过即止）。

官方评分器（official scorer）：冻结提交（submission freeze）后在官方镜像内跑隐藏测试集（FAIL_TO_PASS / PASS_TO_PASS），结果由 Eval 平面持有，拒绝执行器覆盖（修复 #7）——受测系统永远碰不到官方报告。

这一层分离正是"演化集失败模式"的来源：慢性失败案例全部是"过可见、挂官方"——也即系统的自评信号与真实目标存在系统性偏差，这本身是实验的重要测量对象（§9 发现三）。

(e) Coordinator 判决状态机（v3）

H0_RUNNING→ 10 案例全 official_terminal →H0_COMPLETE→ 动态分集 →CANDIDATE_LOCKED
H1_EVOLUTION→H1_REGRESSION→ 归约 →
PILOT_COMPLETE / retain（演化有救援 & 回归全绿） ROLLBACK_AWAITING（任何 observed-regression） BLOCKED（任何 invalid 臂）

三路判决全部在 8 轮中真实触发过（3 retain / 2 rollback / 2 blocked / 1 no-gain），证明状态机各分支不是纸面设计。

2.3 Execution 平面：演化对象只有一个文件

受控变量设计：8 轮演化的修改面恒定为一个文件——.agents/role-skills/execution/writer/autobugfix-writer/SKILL.md（Writer 角色技能）。协议以执行白名单（execution-allowlist）强制这一点：候选补丁触碰其他任何文件都会被 preflight 拒绝。这让"系统改进"退化为干净的单变量实验：改的是什么、diff 多少行、效果如何，全部可比。

2.4 Operator 治理平面：12 步候选链

triage 归因→ request（绑定 triage+预算+基线）→ preflight（白名单/基线/预算校验）→ start→ writer-start（AI 执行修改）→ verify fast→ candidate-commit→ experiment-run（subject 门）→ verify full→ integrate（实验线）→ export-candidate（Eval 冻结）→ H1 全量重测
  • 预算波次：3 → 8 → 16（wave 数 = 精确案例数；16 = 10 真实案例 + 6 个不透明槽位，槽位不泄露案例总数语义）；每波需独立批准（本实验按用户常设授权采用 delegated_agent 委托批准，批准注记入库）。
  • 实验线（experiment line）：候选先集成到独立分支（experiment/exp2-operator-*-main），保留（retain）才推进冻结基线；回滚（rollback）则实验线复位到 H0 检查点——main 永远不被候选直接触碰。
  • 回滚也是一等公民：回滚由服务签发回执（rollback receipt），coordinator 记录后状态机进入 ROLLED_BACK，全程留痕。

2.5 Resume 断点续跑状态机（resume-first）

每案例执行前追加不可变事件 case_attempt_started，完成后追加唯一终态收据（4 种终态：official_terminal / preflight_rejected / execution_infrastructure_invalid / scorer_infrastructure_invalid）。断点续跑时的和解规则：

  1. 校验 append-only 事件链完整性；
  2. 已有合法终态收据的案例直接跳过——已完成的 Writer 执行永不重复；
  3. 对 open intent 只检查其可信 run root：已有完整官方报告则采纳；broker/preflight 失败则结算为 invalid 终态；
  4. 否则结算为 interrupted invalid；
  5. 然后执行下一个缺失案例。

这一设计在实验中反复兑现价值：会话中断、进程被杀、CLI 挂起、宿主故障后，研究都能从断点无损继续（例如 v3r5b 的 sympy 臂在崩溃后被和解为 invalid 收据，其余 9 案例照常完成）。

3.1 三数据集划分（用户定义的权威协议）

集合构成规则
演化集 evolution当前轮 H0 的失败案例（动态派生）每轮根据执行反馈提出假设、修改系统、逐步攻克
回归集 regression当前轮 H0 的通过案例（动态派生）硬门：H1 全量重测，任何一个由通过变失败 → 候选作废、自动回滚

注意演化/回归集是按轮动态重新派生的：同一案例可在不同轮属于不同集合（真实发生过：seaborn 在 v3r3 属回归集、v3r4 属演化集、v3r6 又属回归集）。这使配对始终是"同轮 H0 vs 同轮 H1，除候选外一切输入相同"。

3.2 协议三代演进（本身就是一次协议工程）

版本H1 覆盖教训 → 改进
v2（r4–c8）5 配对案例（2 source + 3 transfer）r4 保留时 scikit-learn（H0 通过）未被重测——回归覆盖不完整，可能漏放回归
v3（v3r3 起）全部 10 案例（演化 ∪ 回归）schema v3、evaluation_mode=iterative_full；"通过的必须始终保持通过"被机器强制执行

v2 → v3 的驱动因素正是第一性原则："通过的应该就是始终保持通过"。v3 首轮（v3r3）立即抓到了 v2 抓不到的回归（seaborn），验证了升级的必要性。

3.3 执行参数（全 8 轮冻结）

  • 模型 gpt-5.4-mini；推理档位 low（v3r6 起 medium，作为受控变量切换，c8 先例）；
  • 每案例最多 2 次 Writer 尝试（attempt-2 需换思路）、单次 900s、并发 1（严格串行）；
  • 校准案例（Flask、Pylint）每 study 先跑，验证装置端到端可用（结果不计入演化统计）；
  • 所有运行钉死 GIT_AUTHOR_DATE/GIT_COMMITTER_DATE 等环境键以保证快照可复现（修复 #4）。

3.4 形式化模型：H=(S, C) 与三通道变更系统

每一代受测 Agent 表示为配置 H = (S, C)：S 为技能指令层（Writer SKILL.md，由选择机制演化的变量，7/8 轮）；C 为算力处理层（推理档位等运行时参数，谱系开关变量，2 次切换）。实验中系统发生过的全部变更分为三类，各自走不同的验证通道——这是归因严格性的结构保证：

变更通道验证义务
ΔS（技能文本）候选通道：白名单锁单文件 → 同轮 H0/H1 配对 → rescue−regression−invalid 选择过回归门才保留（retain）
ΔC（算力档位）谱系开关通道：重定基线（新 H0 重建演化/回归划分），不作为对旧谱系的候选算力效应由跨谱系交互对比确认（同一 S 在两档位下的配对差：c7 no-gain@low vs c8 rescue@medium）
ΔM（装置代码维护，~10 项缺陷修复）维护通道：不经候选选择全量门禁 + subject 门基线 + 涉及测量行为时强制重盖全部 12 案例资格（evaluator_runtime_id 变更即作废）+ 显式中性声明

两点精确说明：(1) c8 被保留的不是"算力候选"而是新谱系（C=medium）下重新配对评估的 S——medium 的证据形态是交互对比而非同轮配对；(2) Memory 与循环策略（max_attempts、停机信号）作为负控制变量冻结，发现三（§9）恰好证明循环策略是下一个应解锁的演化变量。

三通道分离回答了自改进系统的根本问题："改进自己"与"弄坏尺子"如何不混在一起。 若 ΔM 冒充能力改进走候选通道会污染归因；若 ΔS 绕过回归门走维护通道则回归不可拦。本实验中 3/3 的回归拦截率是"ΔS 只能走候选通道"这一约束的结构性结果，而非提议层智力的产物——evaluator_runtime_id 让尺子动了自己会喊（测量代码一变，资格全部自动作废）。

4 Memory 机制设计 Memory as a Controlled Variable

本实验的 Memory 设计回答的问题与主流不同：不是"记忆如何帮助系统"，而是"如何把记忆从实验变量中彻底排除，让演化信号可归因"。

4.1 为什么冻结为空 Memory

若 Writer 可跨轮积累记忆（案例经验、失败教训），则每轮 H0/H1 的表现变化就混杂了两个来源：技能文件的修改（本实验的自变量）与记忆的增长（不可控协变量）。为了让"候选 → 结果"的因果解释成立，实验将 Memory 平面固定为空 fixture（exp2-empty-memory-fixture-v1）：

  • 空 Memory 根目录整体摘要后写入 manifest 与 plan（memory_fixture_digest）；
  • 每次执行前实时重验（修复 #7：bind by fixture digest with live revalidation）——目录内容漂移即拒绝执行；
  • 官方报告由 Eval 平面持有并拒绝执行器覆盖——受测系统不能靠往"记忆"里塞官方结果来作弊。

4.2 这不是缺陷而是设计

Memory-as-variable 是一个实验设计立场：本实验测量的是"技能演化"这一单独杠杆的极限（§9 的平台期结论正是因此才能归因于技能而非其他）。Memory 演化作为正交杠杆，被协议留作后续实验——届时只需解冻 fixture 并重新资格化，装置其余部分不变。工程上 Memory 平面的绑定/重验/防覆盖机制已经齐备，切换成本极低。

5.2 冻结 H0 推进配方（subject advance recipe）

被保留的候选成为下一轮的新冻结 subject。推进是一套机械步骤（全部门禁机器校验）：

  1. 常量 SWE_H0_SUBJECT + 两个 benchmarks YAML 的 h0_subject 同步指向新 SHA；
  2. 重派生 raw-codex 基线的 source_protocol_digest（否则契约测试失败）；
  3. 全量门禁（417 项测试）必须全绿；
  4. 由于常量文件参与 evaluator_runtime_id，全部 12 个案例资格必须重盖（gold×2+null 重放，无模型调用）；
  5. 重新装配：协议 → manifest → 5 项源检查 → 装置回执 → 双案例校准 → operator study → binding → plan → init → H0×10。

6 治理与安全机制 Governance

6.1 防自我背书（anti self-blessing）

  • trusted_ref：治理命令必须显式传锚点提交；guard 身份校验要求调用来自"HEAD==trusted_ref 且树干净"的受保护检出——候选代码不能调 guard 为自己背书；
  • 锚点推进需人工授权（本实验后段按用户常设全权委托执行，委托注记随每次批准入库，全程可审计）；
  • study ID 一次性：烧毁的 ID 永不复用；同一 worktree 禁止并行会话。

6.2 内容寻址审计链

从 triage 到判决报告，每一步产出都带 record_digest 且相互摘要绑定：归因 → 请求 → 批准 → Writer 运行 → 检查 → 候选提交（含完整 diff 摘要）→ 集成 → 候选导出 → H1 收据 → 判决报告。任一环节被篡改，链上后续摘要全部失配。8 轮 × 12 步 ≈ 100 条治理记录全部入库（governance.sqlite3 + 导出 YAML 双形态）。

6.3 沙箱与凭据隔离

Subject 执行环境：bwrap 气泡（--unshare-pid/net、--die-with-parent）、任务工作树为唯一可写目标、凭据路径与敏感环境对受测系统不可见、SDK 请求 cwd 必须等于任务工作树。Writer 的 shell 命令在沙箱内执行，产生的文件变更全部进入补丁摘要账本（§2.2d）。

8 结果分析 Results

8.1 主结论

  1. 回归门 100% 有效：三轮出现 observed-regression（c6 / v3r3 / v3r6），全部被检出并拒绝候选，零漏放；三次被拒候选中有两次是"救回一个案例但弄坏另一个"的净伤害或平手方案——没有门它们都会被误判为"改进"。
  2. 演化有效但边际递减：4 次保留（含 no-gain）将解决率 2/10 推至 5/10（+150%）；前半程每轮可救援 1–2 案例，后半程（v3 时代）救援与回归相互抵消，进入平台期。
  3. 平台期可精确归因：慢性失败核心（astropy、sympy、sphinx）在 low 与 medium、7 种技能假设下从未被攻克；它们全部呈现"过可见测试、挂官方隐藏测试"的同构失败模式。

9 三大实证发现 Findings

发现一：指引 × 算力交互（c8 与 v3r6 双重验证）

同一份"验证类"技能指引，在 low 档位零效果（c7：retain_no_gain），在 medium 档位产生救援（c8：matplotlib；v3r6：seaborn 于 H0、pytest 于 H1）。而纯算力提升本身 +0（c8 的 H0@medium 与 H0@low 同为 4/10 波动带）。

解释：指引只有在推理预算充足时才被模型真正执行（"验证每个需求"需要规划与多步 shell 操作）。这对"该调 prompt 还是该调算力"是一个可量化的回答：两者是乘性关系，不是加性关系。

发现二：跷跷板效应——prompt 级演化无法累积收益

8 轮中的每次救援几乎都伴随另一次回归：c6 救 xarray 坏 matplotlib；v3r4 救 matplotlib（medium 下 v3r6 又失守）；v3r6 救 pytest 坏 seaborn。边缘案例（matplotlib / seaborn / pytest）随技能文本改动反复翻转，解决率在 4–6/10 振荡而非爬升。

解释：单一技能文件服务所有案例，任何全局性措辞变化都会同时移动多个案例的行为分布——对小模型而言信号/噪声比不足以支撑单调改进。这是平台期的根因，也划定了"prompt 演化"这一杠杆的能力边界。

发现三：重试杠杆的结构性不可达

v3r5b 专门检验"换思路重试"指引，结果 0 救援——因为慢性案例第一次尝试就通过可见验证器，循环以可见验证为停机信号，attempt-2 永远不会触发；它们只挂官方隐藏测试，而官方结果在执行时不可见。

含义：这是一条运行时策略性质的结论，不是技能问题——若要让重试杠杆触达此类失败，需要"耗尽尝试数"或"更强自评门"之类的循环策略修改（已列入未来工作）。识别这一点本身就是三集协议 + 逐臂配对带来的可归因性收益。

12 创新点总结（多角度） Contributions

① 协议设计角度

三数据集受控演化协议 + 全量回归硬门：把"系统自我改进"形式化为每轮 H0/H1 同轮配对的受控实验；v2→v3 的升级（H1 从 5 配对到全 10）由真实漏检风险驱动，并被 v3r3 立即验证。对照：业界 prompt 迭代普遍无逐案例配对与回归保障。

② 验证机制角度

双层验证 + 资格三重奏：可见验证器（停机信号）与官方隐藏评分（唯一真值）严格分离；gold×2+null×1 的资格机制先证明"考题有效"再测系统；非干预校验 + 执行器覆盖拒绝防评测被污染。

③ 治理角度

AI 自改系统的 CI 化：12 步治理链 + 预算波次 + 内容寻址审计链 + 实验线/main 隔离 + 服务签发回滚回执。系统的每次自我修改都可追溯到"谁批准、改了什么 diff、检查结果、为何保留/回滚"。这是 Agent 自我改进安全性的一个可运行参考实现。

④ Memory 角度

Memory 作为被控变量而非功能：空 fixture + digest 绑定 + 实时重验，把记忆从演化信号中完全排除，使 8 轮结果可单变量归因；同时为"记忆演化"正交实验预留了切换开关。

⑤ 工程角度

Resume-first 可信批跑：append-only 事件账本 + 四类终态收据 + 崩溃和解规则，使"每案例 10–20 分钟、单轮 3–4 小时"的真实模型批跑在会话中断、进程被杀、CLI 挂起、宿主故障下都能无损续跑——160+ 次执行无一重复。

⑥ 实证发现角度

三条可复用的经验规律：指引×算力乘性交互（§9-一）；prompt 演化的跷跷板边界（§9-二）；以可见验证为停机信号的循环对"过可见挂官方"失败的结构性盲区（§9-三）。每条都由受控配对实验支撑。

13 局限与未来工作 Limitations & Future Work

  • 样本量：10 案例优化集 + 8 轮，统计功效有限；结论表述为"该协议下的实证规律"而非总体推断（报告禁则已声明）。可扩案例集复用全套装置。
  • 平台期未破：三个已识别但未实施的方向——（a）耗尽尝试数 / 更强自评门的循环策略（针对发现三）；（b）解冻 Memory 的正交演化；（c）分案例类型的技能路由（针对跷跷板，把"类型分治"细化到案例级路由以隔离扰动）。
  • held-out 无 Guard 队列：按用户决定以透明普通运行替代密钥随机队列，选样确定性透明但非盲；Avalonia 的 MSBuild 稳定性问题（C# 构建守护进程持续写工作树）待"申报前杀进程树"方案解决后补测。
  • 模型单一：全部结论建立在 gpt-5.4-mini；协议已参数化档位 {low,medium,high,xhigh}，换模型/档位的复跑是纯配置工作。
